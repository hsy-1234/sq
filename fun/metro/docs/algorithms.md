# 武汉地铁趣味题：算法与数据结构详解

本文对应 `fun/metro/` 的当前实现，重点回答三个问题：

1. 地铁数据怎样变成一张可计算的图；
2. “最快、最短、最少换乘”三种方案分别怎样求；
3. DFS、BFS、最小生成树、票价这些功能怎样复用同一套图。

文中的行号以当前源码为准。数据来源、里程校准方法和字段格式见 [`data/README.md`](../data/README.md)。

## 1. 问题与数据规模

### 1.1 输入

数据文件 `fun/metro/data/wuhan_metro.txt` 每行一条记录：

```text
STATION S001 径河
LINE L01 1号线
SEG L01 1 0
STOP L01 S001 1.20 2
STOP L01 S002 1.05 2
TRANSFER S031 4.0
```

含义：

- `STATION`：物理站点，`S001` 是站点 ID，`径河` 是站名；
- `LINE`：线路，`L01` 是线路 ID，`1号线` 是线路名；
- `SEG`：一条线路上的一个连续区段，第三个字段 `0` 表示普通区段，`1` 表示环线区段；
- `STOP`：区段内的一个停靠点，后两个字段是“到下一站”的公里数和分钟数；
- `TRANSFER`：某个换乘站的换乘时间；没有写时使用默认值 4.0 分钟。

### 1.2 当前数据规模

| 项目 | 数量 |
| --- | ---: |
| 线路 | 13 |
| 物理站点 | 298 |
| 线路-站点节点 | 352 |
| 停靠点 `STOP` | 352 |
| 区段 `SEG` | 13 |
| 换乘站 | 49（44 个两线站 + 5 个三线站） |
| 乘车边 | 340 |
| 换乘边 | 59 |
| 线路-站点图边数 | 399 |
| 物理站点图边数 | 338 |
| 线路总里程 | 575.20 km |
| 物理站点图边权和 | 572.28 km |
| 最小生成树 | 297 条边，480.09 km |

这张表里有两个容易混淆的概念：

- **物理站点**：乘客眼中的“一个站”，例如洪山广场；
- **线路-站点节点**：某条线路上的“洪山广场”，例如 2 号线的洪山广场、4 号线的洪山广场。它们是两个不同的图顶点。

后文用“节点”专指线路-站点节点，用“站点”专指物理站点。

### 1.3 三个路径目标

| 目标 | 要最小化的量 | 直观含义 |
| --- | --- | --- |
| `METRO_FASTEST` | 总时间（分钟） | 最快到达 |
| `METRO_SHORTEST` | 总里程（公里） | 路程最短，通常用于票价 |
| `METRO_FEWEST_TRANSFERS` | 换乘次数 | 少折腾 |

这三个目标不能用一个权重同时表达：最快的路线不一定最短，最短的路线可能换乘很多次。因此程序为每个目标准备了一张图。

## 2. 核心建模：线路-站点双节点图

### 2.1 为什么不能只用物理站点

如果图里只有物理站点，那么“在洪山广场从 2 号线换到 4 号线”这件事没有地方存放：

- 把换乘时间加到某条边上，无法区分“坐 2 号线经过洪山广场”和“在洪山广场从 2 号线换到 4 号线”；
- 同一个站点被三条线经过时，换乘费用还取决于“从哪条线来、到哪条线去”。

所以程序把状态拆成两层：

```text
物理站点层（station_graph）
    洪山广场  ── 相邻站之间的公里数 ──  中南路

线路-站点层（time / distance / transfer_graph）
    (L02, 洪山广场) ──乘车 (d, t)──> (L02, 中南路)
          │
       换乘 (0 km, 4 min, 1 次)
          │
    (L04, 洪山广场) ──乘车 (d', t')──> (L04, 中南路)
```

- **线路-站点层**：顶点是 `(线路, 站点)`，乘车边连接同一线路的相邻站，换乘边连接同一物理站点的不同线路。三种路径规划都在这层做。
- **物理站点层**：把同一物理站点的多个线路节点合并成一个顶点，只保留“相邻站点之间的最小公里数”。DFS、BFS、连通性、最小生成树用它。

物理站点层的边数比线路-站点层少，因为它把两条线重复连接的同一对站点合并了。当前数据中线路-站点层有 340 条乘车边，合并后物理站点层剩 338 条边。

### 2.2 节点编号与直接索引

`MetroNode` 只有两个字段：

```c
typedef struct {
    int station;   /* 物理站点下标 */
    int line;      /* 线路下标 */
} MetroNode;
```

为了在建图时快速判断“某条线是否经过某个站”，`MetroNetwork` 里有一张直接索引表：

```c
int *node_lookup;   /* 长度 line_count * station_count */
```

访问方式是：

```c
key  = line * station_count + station;
node = node_lookup[key];   /* -1 表示该线路不经过该站 */
```

这是典型的**直接寻址**：

- 时间 O(1)；
- 空间 O(L × S)。当前 13 × 298 个 `int`，约 15 KB；
- 比“每次遍历节点数组查找”简单，也比哈希表少一层实现。

`node_lookup` 同时被用作一致性检查：对每个节点，反查 `node_lookup[line * S + station]` 必须指回它自己；`metro_validate()` 会检查这一点。

### 2.3 四张图

`MetroNetwork` 里保存了四张无向图：

| 图 | 顶点 | 乘车边权 | 换乘边权 | 用途 |
| --- | --- | --- | --- | --- |
| `time_graph` | 线路-站点节点 | 分钟 | 换乘分钟（默认 4.0） | 最快路径 |
| `distance_graph` | 线路-站点节点 | 公里 | 0 | 最短路径、票价 |
| `transfer_graph` | 线路-站点节点 | 0 | 1 | 最少换乘 |
| `station_graph` | 物理站点 | 公里（重复边取最小） | 无 | DFS/BFS/连通性/MST |

四张图都是 `graph_init(..., false)` 创建的无向图。

为什么不用一张图加“权重函数”？

- 基础库的 `graph_dijkstra()` 接收一张 `Graph`，边权直接存在矩阵里；
- 如果改成“同一张图、不同算法用不同权重”，要么给 Dijkstra 传函数指针，要么在每次查询前改矩阵；
- 四张图的代价是内存，但当前规模很小（见第 8 节），换来的是每种算法都只面对一张普通的带权图，代码更容易讲清楚。

## 3. 建图流程

入口是：

```c
DsStatus metro_load(MetroNetwork *network, const char *path);   /* fun/metro/src/ds_metro.c:773 */
```

它采用“**临时网络 + 两遍扫描 + 校验后交换**”的方式，避免解析失败把旧网络弄坏。

### 3.1 两遍扫描

第一遍只读 `STATION` 和 `LINE`：

```text
打开文件
  ├─ STATION id name  → 追加到 stations[]
  ├─ LINE    id name  → 追加到 lines[]
  ├─ 注释/空行        → 跳过
  └─ 其他记录         → 跳过（留给第二遍）
rewind
第二遍只读 SEG / STOP / TRANSFER
```

为什么必须两遍？

- `STOP L02 S031 ...` 只给出站点 ID，建图时需要把 ID 换成数组下标；
- `SEG` 可能写在它引用的 `LINE` 之前；
- 第一遍先把所有站点和线路收集齐，第二遍就能按 ID 线性查找并解析。

当前实现的 ID 查找是线性的：

- `metro_find_station_by_id()`：O(S)；
- `metro_find_line_index()`：O(L)。

在 298 个站、13 条线的规模下，这点开销远小于后面矩阵初始化的 O(V²)，所以没有为 ID 建哈希表。如果站点数上到几万，应该改成哈希表或排序后二分。

### 3.2 建节点

`metro_build_nodes()`（`fun/metro/src/ds_metro.c:488`）做四件事：

1. 分配 `node_lookup`，长度 `line_count * station_count`，全部填 `-1`；
2. 遍历每个区段的每个停靠点：

   ```c
   key = line * station_count + station;
   if (node_lookup[key] == -1) {
       /* 新建一个 MetroNode{station, line} */
       node_lookup[key] = new_index;
   }
   ```

3. 反向填充每个物理站点的 `lines[]` 和 `line_count`：

   ```c
   station->lines[station->line_count++] = line;
   ```

4. 累加每条线路的 `total_km`，并把 `line_count >= 2` 的站点标记为换乘站。

因为 `node_lookup` 保证同一个 `(line, station)` 只创建一个节点，所以节点数正好等于“线路-站点”组合数，当前为 352。

### 3.3 建边

`metro_build_graphs()`（`fun/metro/src/ds_metro.c:595`）先创建四张图，再逐条加边。

#### 乘车边

对每个区段，取相邻的两个停靠点：

```c
for (i = 0; i + 1 < segment->stop_count; ++i) {
    from = stops[segment->first_stop + i].station;
    to   = stops[segment->first_stop + i + 1].station;
    /* 加边 */
}
```

- `time_graph`：权重 = `minutes_to_next`；
- `distance_graph`：权重 = `km_to_next`；
- `transfer_graph`：权重 = 0（坐车不算换乘）；
- `station_graph`：权重 = `km_to_next`，同一对物理站点重复出现时取最小值。

#### 环线闭合边

普通区段的最后一个停靠点没有“下一站”，它的 `km_to_next` 和 `minutes_to_next` 写 0。环线区段需要额外把“最后一个停靠点 → 第一个停靠点”连起来：

```c
if (segment->loop && segment->stop_count > 1) {
    /* 最后停靠点 → 第一个停靠点 */
    /* 权重取最后停靠点记录的 km_to_next / minutes_to_next */
}
```

12 号线是环线。数据里它的最后一个停靠点是省农科院南，闭环边回到楚祥大道，长度 1.11 km、2 分钟。这条边是数据文件里唯一一个“末站后两个字段非 0”的地方；`data/README.md` 对此有说明。

#### 换乘边

对每个物理站点，把它经过的线路两两配对：

```text
若站点有 k 条线：
  k = 2：加 1 条换乘边
  k = 3：加 3 条换乘边（三角形）
  k = 4：加 6 条换乘边
```

当前数据中：

- 44 个两线站：44 × 1 = 44 条；
- 5 个三线站：5 × 3 = 15 条；
- 合计 59 条换乘边。

每条换乘边：

| 图 | 权重 |
| --- | ---: |
| `time_graph` | 该站的 `transfer_minutes`，没有 `TRANSFER` 记录时为 4.0 |
| `distance_graph` | 0 |
| `transfer_graph` | 1 |
| `station_graph` | 不加换乘边 |

三线站用三角形而不是“串成一条链”，是为了让任意两条线之间都只算一次换乘：

```text
        L02
       /   \
    4 min  4 min
     /       \
   L04───────L11
       4 min
```

如果串成 `L02—L04—L11`，从 L02 到 L11 会被算成两次换乘，不符合实际。

#### 并行边去重

同一对节点之间可能出现多条边，例如：

- 两条线路都连接同一对物理站点；
- 某个区段重复经过同一对站点；
- 未来数据中出现分支/重复区段。

`metro_add_shorter_edge()`（`fun/metro/src/ds_metro.c:581`）的规则是：

```text
if (u == v) 跳过自环
if (已有边 old_weight <= 新权重) 保留旧边
else 用新权重覆盖旧边
```

这样每对节点最多保留一条边，且保留的是最小权重。对 `station_graph` 来说，这正好实现“两条线重复连接同一对站点时，只留较短的里程”。

### 3.4 加载事务与校验

`metro_load()` 不会直接往调用者传进来的网络里写：

```text
MetroNetwork next = {0};
第一遍解析 → next
第二遍解析 → next
metro_build_nodes(&next)
metro_build_graphs(&next)
next.loaded = true
metro_validate(&next)
  成功 → metro_network_destroy(network); *network = next;
  失败 → metro_network_destroy(&next); 返回错误，旧网络保持不变
```

这是一个小型的“事务”：

- 解析到一半失败，不会留下半张图；
- 校验失败，调用者原来的网络仍然可用；
- 结构体按值交换，不需要逐字段拷贝。

`metro_validate()`（`fun/metro/src/ds_metro.c:1546`）检查的主要不变量：

- 至少有一条线路、一个站点、一个区段、一个停靠点、一个节点；
- 每条线路至少 2 个站、至少 1 个区段，`total_km` 有限且非负；
- 每个站点的 `line_count` 在 1..8 之间，`is_transfer` 与 `line_count >= 2` 一致；
- 每个区段至少 2 个停靠点，`first_stop + stop_count` 不越界，区段内没有重复站点；
- 每个停靠点的公里数、分钟数有限且非负；
- `node_lookup` 的反查关系成立；
- `station_graph` 连通。

最后一条很重要：如果数据把网络切成两块，`metro_plan()` 对跨块查询会返回不可达；当前数据经过补齐后是全图连通的，校验会拦住以后误改数据造成的断网。

## 4. 三种路径规划

统一入口是：

```c
DsStatus metro_plan(const MetroNetwork *network,
                    int from, int to,
                    MetroCriterion criterion,
                    MetroPath *path);   /* fun/metro/src/ds_metro.c:1295 */
```

它做四步：

1. 按 `criterion` 选图；
2. 对起点站的每个线路节点各跑一次 Dijkstra；
3. 对终点站的每个线路节点各取一次路径；
4. 用“主目标 + 平局规则”选出最好的一条，并重算距离、时间、换乘数和票价。

### 4.1 Dijkstra

基础库的 Dijkstra 在 `src/ds_graph.c:652`，采用**邻接矩阵 + 线性找最小**的实现：

```text
dist[]  全部 INF，dist[source] = 0
prev[]  全部 -1
visited[] 全部 false

重复 V 次：
    u = 未访问节点中 dist 最小的
    若不存在或 dist[u] == INF：结束
    visited[u] = true
    对每个 v：
        w = matrix[u][v]
        若 !visited[v] 且 w != INF 且 dist[u] + w < dist[v]：
            dist[v] = dist[u] + w
            prev[v] = u
```

复杂度：

- 外层 V 次，内层找最小 O(V)，松弛 O(V)；
- 总计 O(V²)；
- 空间 O(V)（`dist`、`prev`、`visited`），矩阵本身是 O(V²)。

为什么可以用 Dijkstra：

- 所有边权非负：解析阶段拒绝负数，校验阶段再检查一次；
- 有负权时 Dijkstra 的“选最小即最终”不成立，需要 Bellman-Ford。

正确性直觉：

> 当 u 被选为未访问节点中 dist 最小时，任何从 source 到 u 的更短路径，都必须先经过某个已访问节点 x，再从 x 走到某个未访问节点 y。由于边权非负，这条路径到 y 的前缀不会比 dist[u] 更短，而 y 在之前就该被选中，矛盾。

### 4.2 三种目标对应三张图

| `criterion` | 使用的图 | 乘车边 | 换乘边 | Dijkstra 最小化的量 |
| --- | --- | ---: | ---: | --- |
| `METRO_FASTEST` | `time_graph` | 分钟 | 4.0 分钟 | 总时间 |
| `METRO_SHORTEST` | `distance_graph` | 公里 | 0 | 总里程 |
| `METRO_FEWEST_TRANSFERS` | `transfer_graph` | 0 | 1 | 换乘次数 |

几个容易忽略的点：

- **最短路径图里换乘边是 0 公里**：换乘本身不产生运营里程，所以算法可能为了省 0.29 km 而多换乘几次。第 4.7 节的实例就是这个现象。
- **最少换乘图里乘车边是 0**：Dijkstra 累加的是换乘边条数，坐多少站都不影响目标值。
- **最快图里换乘是 4 分钟**：这个值来自站点的 `transfer_minutes`，数据里没有逐站设置时用默认 4.0。它把“走路、等车、上下楼”压缩成一个固定惩罚。

### 4.3 多起点 / 多终点

这是整个实现里最关键的一步。

一个物理站点可能对应多个线路节点。例如洪山广场同时是 2 号线和 4 号线的节点：

```text
(L02, 洪山广场)   dist = 0   ← 从 2 号线出发
(L04, 洪山广场)   dist = 0   ← 从 4 号线出发
```

`metro_plan()` 的做法是：

```text
best = 空
for 每个节点 s：
    if s.station != from: continue
    dijkstra(图, s, dist, prev)
    for 每个节点 t：
        if t.station != to: continue
        if dist[t] 不可达: continue
        path = 从 prev 回溯 s → t
        计算 path 的距离、时间、换乘数
        若比 best 好：best = path
```

为什么不能随便选一个起点节点？

- 如果起点站有 3 条线，选错线路会凭空多一次换乘，或者直接错过更快的线路；
- 从物理站点出发时，乘客可以自由选择任意一条经过该站的线路，**上车前不需要换乘**，所以每个起点节点的初始距离都应为 0；
- 终点同理：到达终点站后，停在哪条线的站台都可以出站，**下车后不需要换乘**，所以每个终点节点都可以作为结束。

这等价于在图上加一个“超级源点”，用 0 权边连到起点的所有线路节点；再加一个“超级汇点”，用 0 权边连到终点的所有线路节点。当前实现没有真的加这两个临时节点，而是直接枚举，原因是：

- 枚举代码更直观，不需要修改图；
- 起点/终点的线路数最多 8，枚举量很小；
- 超级源点还要处理“临时加边、查询后删边”，反而容易出错。

代价是：起点有 `k_s` 条线时，要跑 `k_s` 次 Dijkstra；终点有 `k_t` 条线时，每次 Dijkstra 后要检查 `k_t` 个目标节点。当前 `k <= 8`，完全可以接受。

### 4.4 路径还原

Dijkstra 只给出 `prev[]`，`metro_reconstruct_path()`（`fun/metro/src/ds_metro.c:1189`）负责把它变成节点序列：

```text
从 target 开始，沿 prev 一直走到 source
每走一步把节点压入临时数组
若走了 V 步还没到 source：路径非法，返回错误
若最后不是 source：路径非法
反转临时数组 → path->nodes
```

几个保护：

- 路径长度不能超过节点总数，防止 `prev` 成环导致死循环；
- 必须回到指定的 source，防止从别的起点回溯；
- 反转后 `path->nodes[0]` 是起点，`path->nodes[count-1]` 是终点。

### 4.5 指标重算

Dijkstra 的 `dist[t]` 只给出“主目标”的最优值：

- 最快图给出时间，但没给距离；
- 最短图给出距离，但没给时间；
- 最少换乘图给出换乘数，但没给时间/距离。

`metro_measure_path()`（`fun/metro/src/ds_metro.c:1226`）沿路径重新累加：

```text
distance_km = Σ distance_graph 上每条边的 km
time_min    = Σ time_graph 上每条边的 minutes
transfers   = 路径中“同一物理站点、不同线路”的次数
```

为什么这三条边一定能在对应图里找到？

- 建图时，每条乘车边和换乘边都同时加进了 `time_graph`、`distance_graph`、`transfer_graph`；
- 因此同一条路径在三张图上都可测量；
- `graph_has_edge()` 是矩阵查询，O(1)。

换乘计数的条件是“同一站点 + 不同线路”：

- 同一线路的相邻节点之间是乘车边，不会触发；
- 从 `(L02, 洪山广场)` 到 `(L04, 洪山广场)` 是换乘边，触发一次；
- 路径中线路变化一定发生在同一物理站点，因为乘车边不改变线路。

### 4.6 平局规则

三种目标各自有一个主指标。主指标相同或差小于 `1e-9` 时，`metro_candidate_better()`（`fun/metro/src/ds_metro.c:1257`）按下面的顺序比较：

| 目标 | 第 1 优先 | 第 2 优先 | 第 3 优先 | 第 4 优先 |
| --- | --- | --- | --- | --- |
| 最快 | 时间 | 距离 | 节点数 | — |
| 最短 | 距离 | 时间 | 节点数 | — |
| 最少换乘 | 换乘数 | 时间 | 距离 | 节点数 |

`1e-9` 是浮点比较的容差，避免 `18.719999999` 和 `18.720000001` 被当成不同值。

需要说明一个实现边界：

> 平局规则只在“每个起点-终点节点对由 Dijkstra 返回的那一条路径”之间比较。Dijkstra 在松弛时用的是严格小于 `dist[u] + w < dist[v]`，主目标相同的另一条路径不会被保留下来。因此它不保证在所有主目标最优的路径中，次目标也全局最优。

如果课程要求严格的字典序最优（先比主目标，再比次目标，再比第三目标），需要把权重编码成元组，或者在松弛时做多目标比较；当前实现选择的是“主目标严格最优 + 次目标尽力而为”，在 352 个节点的规模下已经足够，代码也简单得多。

### 4.7 实例：宏图大道 → 武昌火车站

下面三组数据来自 `build/bin/metro.exe` 的实际运行结果。

#### 最快

```text
8号线：宏图大道 → 塔子湖 → 中一路 → 竹叶山 → 赵家条 → 黄浦路 → 徐家棚
换乘 7号线：徐家棚 → 湖北大学 → 新河街 → 螃蟹岬 → 小东门 → 武昌火车站

19.01 km，38.0 分钟，1 次换乘，6 元
```

#### 最短

```text
8号线：宏图大道 → 塔子湖 → 中一路 → 竹叶山 → 赵家条
换乘 3号线：赵家条 → 惠济二路 → 香港路
换乘 6号线：香港路 → 苗栗路 → 大智路 → 江汉路
换乘 2号线：江汉路 → 积玉桥 → 螃蟹岬
换乘 7号线：螃蟹岬 → 小东门 → 武昌火车站

18.72 km，49.0 分钟，4 次换乘，6 元
```

#### 最少换乘

与最快方案相同：

```text
19.01 km，38.0 分钟，1 次换乘，6 元
```

#### 这三个结果说明了什么

- 最短方案只省了 `19.01 - 18.72 = 0.29 km`，却多换乘 3 次、多花 11 分钟；
- 原因是 `distance_graph` 里换乘边的权重是 0：换乘不增加里程，算法就会用换乘去“抄近路”；
- 最快方案和最少换乘方案恰好重合，因为 8 号线转 7 号线只需要一次换乘，而且时间也最短；
- 三种方案的里程都落在 18–24 km 区间，所以票价都是 6 元。

这正是“不同目标需要不同图”的最好例子：如果只保留一张图，就无法同时解释这三种结果。

### 4.8 票价

`metro_fare()`（`fun/metro/src/ds_metro.c:1138`）使用分段计价：

| 里程 `d`（km） | 票价（元） |
| --- | ---: |
| `0 <= d <= 4` | 2 |
| `4 < d <= 8` | 3 |
| `8 < d <= 12` | 4 |
| `12 < d <= 18` | 5 |
| `18 < d <= 24` | 6 |
| `24 < d <= 32` | 7 |
| `32 < d <= 40` | 8 |
| `40 < d <= 50` | 9 |
| `50 < d < 70` | 9 |
| `70 <= d < 90` | 10 |
| `90 <= d < 110` | 11 |

超过 50 km 后每 20 km 加 1 元。代码里的 `1e-9` 用来处理浮点边界，让恰好 4.0、8.0、12.0 这样的值落在较低的一档；这与测试用例的期望一致：

```text
4.00 → 2    4.01 → 3
8.00 → 3    8.01 → 4
12.00 → 4   12.01 → 5
18.00 → 5   18.01 → 6

50.00 → 9   50.01 → 9
70.00 → 10  90.00 → 11
```

## 5. 全图遍历与连通性

### 5.1 为什么用物理站点图

路径规划需要区分线路，所以用线路-站点图；但下面这些问题只关心“站点是否被走到”：

- 从某个站出发能否到达所有站；
- 图的连通分量；
- 课程设计里的 DFS/BFS 演示。

这时应该用 `station_graph`：

- 顶点就是 298 个物理站点；
- 同一对站点被多条线连接时只保留一条最短边；
- 不会有“同一个洪山广场被访问两次”的问题。

如果在线路-站点图上做 DFS/BFS，洪山广场会以 `(L02, 洪山广场)`、`(L04, 洪山广场)` 等身份出现多次，遍历结果不再是“访问了多少个站”。

### 5.2 DFS

`metro_dfs()`（`fun/metro/src/ds_metro.c:1471`）调用基础库的 `graph_dfs()`（`src/ds_graph.c:554`）：

- 递归实现；
- 进入节点时标记 `visited`；
- 沿邻接表访问所有未访问邻居；
- 时间复杂度 O(V + E)；
- 空间复杂度 O(V)（`visited` + 递归栈）。

当前 298 个站，递归深度最坏 298，默认栈空间足够。如果以后站点数上到十万级，应改成显式栈，避免栈溢出。

### 5.3 BFS

`metro_bfs()`（`fun/metro/src/ds_metro.c:1495`）调用 `graph_bfs()`（`src/ds_graph.c:590`）：

- 用数组实现队列；
- 入队时标记 `visited`，避免同一节点重复入队；
- 按“边数”分层访问；
- 时间复杂度 O(V + E)。

BFS 的“最短”是**边数最少**，不是时间最少、里程最短或换乘最少：

- 一条直达但绕远的线路，边数可能很少；
- 一次换乘但每段都很长的线路，边数可能更少或更多；
- `transfer_graph` 的边权是 0/1，普通 BFS 只数边数，不区分“乘车边 0”和“换乘边 1”，所以不能用它求最少换乘。

求最少换乘可以用 **0-1 BFS**（双端队列：0 权边放队首，1 权边放队尾），复杂度 O(V + E)。当前代码统一用 Dijkstra，是为了让三种目标共用同一套接口；在 352 个节点上，O(V²) 的 Dijkstra 和 O(V+E) 的 0-1 BFS 都很快。

### 5.4 连通性

`graph_is_connected()`（`src/ds_graph.c:1040`）在矩阵上做一次 BFS：

- 从 0 号顶点出发；
- 用 `visited[]` 标记；
- 最后检查是否所有顶点都被访问；
- 时间复杂度 O(V²)（每次找邻居要扫描一行矩阵）。

它被 `metro_validate()` 用来检查整张物理站点图是否连通。当前数据全图连通，所以 `metro_plan()` 对任意两个站都能给出路径；如果数据被误改成两块，加载阶段就会报错，而不是等到查询时才发现不可达。

## 6. 最小生成树

`metro_mst()`（`fun/metro/src/ds_metro.c:1519`）在 `station_graph` 上求最小生成树，边权是公里数。

### 6.1 Prim

`graph_prim()`（`src/ds_graph.c:821`）是稠密图版本：

```text
lowcost[]  当前树到每个顶点的最小边权，初始 INF
parent[]   该最小边对应的树内顶点
visited[]  是否已加入树

从 0 号顶点开始，lowcost[0] = 0
重复 V 次：
    选未访问且 lowcost 最小的顶点 u
    visited[u] = true
    对每个未访问的 v：
        若 matrix[u][v] < lowcost[v]：
            lowcost[v] = matrix[u][v]
            parent[v] = u
```

复杂度 O(V²)，空间 O(V)。它不依赖邻接表，适合边比较多的图；当前 `station_graph` 只有 338 条边，其实算稀疏图，但 V=298 很小，O(V²) 仍然很快。

### 6.2 Kruskal

`graph_kruskal()`（`src/ds_graph.c:951`）：

1. 扫描矩阵上三角，收集所有存在的边

   ```text
   for i in 0..V-1:
       for j in i+1..V-1:
           if matrix[i][j] != INF:
               收集 (w, i, j)
   ```

2. 按权重 `qsort` 排序；
3. 依次取边，用并查集判断两端是否已连通：

   ```text
   若 find(u) != find(v):
       选这条边
       union(u, v)
       边数 +1
       若边数 == V-1：结束
   ```

4. 若结束时边数不足 V-1，说明图不连通，返回错误。

并查集在 `src/ds_graph.c:919`，带**路径减半**：

```c
parent[x] = parent[parent[x]];
```

它把查找路径上的节点隔代指向祖父，均摊接近 O(α(V))。

Kruskal 的复杂度：

- 收集边扫描上三角 O(V²)；
- 排序 O(E log E)；
- 并查集近似 O(E α(V))；
- 总计 O(V² + E log E)。

当前 `station_graph`：V=298，E=338，两种算法都得到：

```text
297 条边，总权值 480.09 km
```

### 6.3 MST 的含义与边界

最小生成树回答的是：

> 如果只用现有站点之间的相邻关系，把所有站点连成一个连通网络，最少需要多少公里的边？

它不是一条乘客路径，也不涉及换乘：

- 树上两个站之间的路径不一定是地铁实际最短路径；
- MST 不含换乘边；
- 同一对物理站点有多条线路时，`station_graph` 只保留最短的那条，另一条线路的轨道不会进入 MST。

当存在相同权值的边时，MST 可能不唯一。Prim 和 Kruskal 选出的边集可能不同，但总权值一定相同。测试只断言“边数 = V-1、总权值一致”，不断言两棵树的边集完全相同，这是正确的做法。

## 7. 正确性与边界情况

### 7.1 路径规划的正确性

分三层看：

1. **单次 Dijkstra**：边权非负，选最小即最终，标准正确性成立。
2. **多起点/多终点**：任何一条从物理站 A 到 B 的路线，必定从 A 的某个线路节点出发、到 B 的某个线路节点结束；枚举所有组合不会漏掉最优解。
3. **目标映射**：
   - 时间图上的路径和 = 总时间；
   - 距离图上的路径和 = 总里程；
   - 换乘图上的路径和 = 换乘次数。

因此三个主目标分别取得最优。

需要区分“主目标最优”和“次目标也最优”：如 4.6 节所述，平局规则是尽力而为，不是严格的字典序多目标优化。

### 7.2 边界情况

| 情况 | 行为 |
| --- | --- |
| 起点 == 终点 | 找到同一个节点，路径长度 1，0 km / 0 分钟 / 0 次换乘，票价 2 元 |
| 起点或终点有多条线 | 枚举所有线路节点，上车/下车不额外计换乘 |
| 三线换乘站 | 三条换乘边组成三角形，任意两线之间一次换乘 |
| 环线 | 最后一个停靠点连回第一个停靠点；12 号线闭环 1.11 km / 2 分钟 |
| 不可达 | `metro_plan()` 返回 `DS_ERR_NOT_FOUND`；当前数据全连通，不会触发 |
| 非法站点下标 | 返回 `DS_ERR_RANGE` |
| 非法目标枚举 | 返回 `DS_ERR_RANGE` |
| 数据里有重复站点 | `metro_validate()` 拒绝加载 |
| 数据里有负数/非有限数 | 解析或校验拒绝 |
| 数据把网络切成两块 | `metro_validate()` 的连通性检查拒绝加载，旧网络保持不变 |
| 空网络 | 生命周期函数和测试覆盖，不会崩溃 |

### 7.3 为什么解析阶段就拒绝负数

Dijkstra 的正确性依赖非负边权。如果允许负的公里数或分钟数：

- 可能构造出负权环；
- “选最小即最终”不再成立；
- 票价的分段函数也会失去意义。

所以 `metro_parse_double()`（`fun/metro/src/ds_metro.c:118`）和 `metro_validate()` 都要求 `isfinite(x) && x >= 0`。换乘时间还额外要求 `> 0`，避免出现“零成本换乘”这种不现实的数据。

## 8. 复杂度与内存

设：

- `V` = 线路-站点节点数，当前 352；
- `E` = 线路-站点图边数，当前 399；
- `S` = 物理站点数，当前 298；
- `L` = 线路数，当前 13；
- `k` = 单个站点最多线路数，当前 3，结构体上限 8；
- `k_s`、`k_t` = 起点、终点的线路数。

### 8.1 时间

| 阶段 / 算法 | 复杂度 | 当前规模下的大致量级 |
| --- | --- | --- |
| 第一遍解析 | O(S² + L² + 行数) | 很小 |
| 第二遍解析 | O(停靠点数 × (S + L)) | 约 11 万次比较 |
| 建节点 | O(V + L×S + 站点线路数) | 很小 |
| 建四图 | 矩阵初始化 O(V²) 占主导，边插入近似 O(E) | 约 12 万次矩阵写入/图 |
| 单次 Dijkstra | O(V²) | 约 25 万次内层操作 |
| `metro_plan` | O(k_s × V² + k_s × k_t × V) | k ≤ 8，最坏约 100 万次 |
| DFS / BFS | O(V + E) | 约 640 次邻居访问 |
| Prim | O(S²) | 约 9 万次 |
| Kruskal | O(S² + E_s log E_s) | 约 9 万次 + 338 条边排序 |
| 校验 | O(S² + Σ 区段停靠点数²) | 很小 |

注意 `metro_plan()` 的复杂度不是 O(V²)，而是 `k_s` 次 Dijkstra。当前大多数站点只有 1 条线，只有换乘站才会跑多次；最坏是三线站出发、三线站到达，`k_s = k_t = 3`，也就是 3 次 Dijkstra + 9 次路径测量。

### 8.2 空间

四张图的矩阵是大头：

```text
time_graph:      352 × 352 × 8 B = 991,232 B ≈ 968 KiB
distance_graph:  352 × 352 × 8 B = 991,232 B ≈ 968 KiB
transfer_graph:  352 × 352 × 8 B = 991,232 B ≈ 968 KiB
station_graph:   298 × 298 × 8 B = 710,432 B ≈ 694 KiB
------------------------------------------------------------
合计                                    3,684,128 B ≈ 3.51 MiB
```

其余结构都很小：

- `node_lookup`：13 × 298 × 4 B ≈ 15 KB；
- 298 个 `MetroStation`：每个约 120 B，约 35 KB；
- 352 个 `MetroStop`：每个 24 B，约 8 KB；
- 352 个 `MetroNode`：每个 8 B，约 3 KB；
- 邻接表边节点：每张图约 2E 个 `GraphArc`，每个 24 B，四张图合计约 70 KB；
- 顶点名：每张图 `V × 32 B`，四张图合计约 45 KB。

整个网络远小于 10 MB，在课程设计规模下没有内存压力。

但矩阵的 O(V²) 是硬上限：

- V = 1,000：单图 8 MB，四图约 30 MB；
- V = 10,000：单图 800 MB，四图约 3 GB，不可行。

如果要把这套代码扩展到全国地铁，必须把矩阵换成邻接表 + 二叉堆 Dijkstra，或者对稀疏图用 0-1 BFS / A*。当前选择矩阵，是因为 V=352，而且矩阵让 `graph_has_edge()` 和 Dijkstra 的松弛都非常直观。

## 9. 设计取舍

### 9.1 为什么用四张图，而不是一张图

**选择**：时间、距离、换乘各一张图，再加一张物理站点图。

**理由**：

- 三种目标的边权语义不同，分开后每张图都是一张普通带权图；
- Dijkstra 不需要知道“现在优化的是哪个目标”；
- 调试时可以直接打印某张图的边权，容易定位问题。

**代价**：内存约 3.5 MiB，建图时要重复插入边。

**替代方案**：一张图 + 权重函数指针，或把权重编码成 `(主, 次, 三)` 元组做多目标 Dijkstra。前者省内存但接口复杂，后者能严格处理平局，但实现难度高。

### 9.2 为什么用矩阵，而不是邻接表

**选择**：`Graph` 同时保存 `double *matrix` 和 `GraphArc **adj`。

**理由**：

- 矩阵让 `graph_has_edge()` O(1)，Dijkstra 的松弛直接扫一行；
- 邻接表让 DFS/BFS 只访问真实邻居，O(V+E)；
- 两者共存，按算法选合适的那一个。

**代价**：矩阵 O(V²) 空间，稀疏图浪费大。

**替代方案**：只用邻接表 + 二叉堆 Dijkstra，空间 O(V+E)，时间 O((V+E) log V)。在 V=352 时两者都很快，矩阵实现更短。

### 9.3 为什么枚举多起点，而不是加超级源点

**选择**：对起点站的每个线路节点各跑一次 Dijkstra。

**理由**：

- 不需要临时修改图；
- 起点/终点线路数最多 8，枚举量可控；
- 路径还原时天然知道是哪条线路出发，便于统计换乘。

**代价**：`k_s` 次 Dijkstra。

**替代方案**：加一个临时超级源点，用 0 权边连到所有起点节点；查询完再删除。这样只需一次 Dijkstra，但临时加边/删边会破坏图的只读性，代码更复杂。

### 9.4 为什么最少换乘也用 Dijkstra

**选择**：`transfer_graph` 上跑 Dijkstra。

**理由**：

- 三种目标共用 `graph_dijkstra()`，接口统一；
- 边权只有 0 和 1，Dijkstra 当然正确；
- 352 个节点，O(V²) 足够快。

**代价**：当前矩阵版 Dijkstra 是 O(V²)，0-1 BFS 是 O(V+E)，后者在稀疏大图上更合适。

**替代方案**：0-1 BFS，用双端队列，O(V+E)。如果以后图变大，这是最直接的优化。

### 9.5 换乘时间为什么是固定 4 分钟

**选择**：每个站一个 `transfer_minutes`，默认 4.0。

**理由**：

- 数据源没有逐站换乘时间；
- 固定值让模型简单，三种目标的差异更容易解释；
- 数据结构已经支持 `TRANSFER` 记录逐站覆盖，未来可以补真实值。

**代价**：大型换乘站（如武汉火车站、洪山广场）与实际换乘时间可能差很多。

**改进**：按站点规模、是否同台换乘、步行距离分别设值；或者把换乘时间拆成“步行 + 等待”。

### 9.6 没有站外步行换乘

当前模型把“武汉站东广场”“武汉站西广场”“武汉火车站”当成不同站点，武昌站东广场、汉口站北广场等也没有做站外步行连接。

**理由**：

- 高德数据里它们是不同的站点 ID；
- 强行合并会改变站名和线路归属，容易引入错误；
- 课程设计重点是图算法，不是步行网络。

**代价**：跨广场换乘会被算成“不可达”或绕远。

**改进**：增加一类“步行边”，权重为步行分钟/公里，连接不同站名的同一交通枢纽；或者建立“站点组”，组内换乘走特殊规则。

### 9.7 物理站点图为什么只留最小边

**选择**：同一对物理站点被多条线连接时，`station_graph` 只保留最短的公里数。

**理由**：

- DFS/BFS/MST 只关心“站点之间是否相邻”，不关心有几条轨道；
- 保留多条平行边会让 MST 的边数和连通性判断复杂化；
- 取最小符合“走较短的那条”的直觉。

**代价**：MST 的总权值不是“所有轨道长度”，而是“每个相邻站对取最短后的最小连通树”。

### 9.8 平局规则是尽力而为

如 4.6 节所述，当前实现保证主目标最优，但不保证在主目标最优的所有路径中次目标也最优。

**理由**：

- 严格的多目标 Dijkstra 需要比较元组，`dist[]` 不再是单个 `double`；
- 课程设计的主要评分点是三种目标能否分别正确求解，次目标的完全最优不是必须；
- 主目标相同的情况在真实数据中不多，实际影响很小。

**改进**：在松弛时用 `(primary, secondary, tertiary)` 字典序比较；或者给主目标加一个极小的次目标惩罚（要注意浮点精度和量纲）。

## 11. 小结

这套实现的骨架可以概括为：

```text
数据文件
  │  两遍解析
  ▼
物理站点 + 线路 + 区段 + 停靠点
  │  建节点、建边
  ▼
线路-站点图（时间 / 距离 / 换乘）  +  物理站点图
  │                                    │
  │ Dijkstra × 3 种权重                 │ DFS / BFS / Prim / Kruskal
  ▼                                    ▼
最快 / 最短 / 最少换乘路径            遍历、连通性、最小生成树
  │
  │ 回溯 + 重算指标 + 分段票价
  ▼
MetroPath
```

最值得记住的三点：

1. **状态要带线路**：只在物理站点上做最短路，无法正确表达换乘；线路-站点双节点图把“当前在哪条线”变成图的一部分。
2. **目标决定边权**：最快用分钟，最短用公里，最少换乘用 0/1；同一张图不可能同时优化三个目标。
3. **多起点/多终点不能省**：起点和终点的每条线路都是一个合法的上下车位置，枚举它们才能不漏最优解。
